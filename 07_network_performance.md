## qperf

Gather bandwidth and latency between two hosts using **qperf**, on the server host:

```bash prompt:"[root@sysperf ~]#"
qperf
```

On the client hosts:

```bash prompt:"[root@sysperf-client ~]#"
qperf sysperf tcp_bw tcp_lat
```

```result

    bw  =  632 MB/sec
tcp_lat:
    latency  =  111 us
```

It reports that the bandwidth is 632 MB/s.

## Packet Tx/Rx and Bottlenecks

On transmitting (Tx):
1. Data is written to a socket which is put in the transmit buffer
2. Kernel encapsulates data into a protocol data unit (PDU)
3. The PDUs move to the per-device transmit queue
4. The network driver copies the PDU from the queue to the NIC
5. NIC sends data and raises an interrupt when transmitted

On receiving (Rx):
1. NIC receives a frame and uses Direct Memory Access (DMA) to copy this into the receive buffer
2. NIC raises a *hard interrupt*
3. Kernel picks up and forwards to the IP layer
4. IP header is further processes, and will be delivered

Potential bottlenecks:
- While handling incoming packets (Rx), during the *hard interrupt* generated by the kernel, a livelock occurs. This preempts everything, which could cause receive buffers to fill up
- NIC hardware buffer can be a problem, the `ethtool` shows dropped packets, this could be a need for an increase of hardware buffer queue
- Application **receives queue** needs sufficient place to handle all incoming packets
	- An important part of the networking performance where you can optimize here


## Kernel Network Tunables

- Some tunables in the kernel network have a minimum, default, and maximum value
- Kernel auto adjust within the range of these values
- `net.ipv4.tcp_mem`, `net.ipv4.udp_mem` has a system-wide memory limits for all networking in **bytes** set as min, pressure, and max
	- min is the minimal amount
	- pressure is when the kernel starts auto-tuning its memory usage
	- max is the maximum amount
	- `getconf PAGESIZE` to get the memory page size, default is 4KiB
- `net.core.rmem_max`, `net.core.wmem_max` a value in bytes that sets the core networking maximum socket receive/send buffers
- `net.ipv4.tcp_rmem`, `net.ipv4.tcp_wmem` is the 
- `netdev_max_backlog` is the maximum number of packets, queued on the INPUT side, when the interface receives packets faster than kernel can process them

## Bandwidth Delay Product (BDP)

- The buffer size as set in `rmem_max` and `wmem_max` is calculated by estimating the amount of data that can fit in a network link between source and destination in a data flow
- The size of the link is the capacity in *bytes per second throughput*, multiplied by the length of the link which is measured in *seconds needed for the round trip delay*
- To calculate round trip time (RTT), use the output of the ping command which is expressed in milliseconds and convert to seconds
- If the network has a throughput of 1Gbps, the calculation is `1,000,000,000 * 0.000228 = 228,000 bits = 28,500 bytes = 27,84KiB` which is the BDP

The methodology for calculating the BDP:
1. Find the round trip time (RTT), and convert milliseconds to seconds `1000ms = 1s`
2. Multiply the throughput (Gbps, Mbps) by the RTT
3. Divide the output by 8 (8 bit = 1 byte) to convert it to bytes
4. Make sure that `net.core.rmem_max` and `net.core.wmem_max` are set equal to or *slightly* greater than the BDP
5. If BDP is higher than **64 KiB**, TCP connection can use window scaling `net.ipv4.tcp_window_scaling = 1`
6. Notice the `rmem_max` and `wmem_max` can never be higher than the max value of `tcp_max`, otherwise it indicates something is wrong

Window Scaling:
- TCP connections use window scaling if the BDP goes above 64KiB
- A window is the amount of data sent that has not yet been acknowledged
- If unacknowledged data goes beyond the windows size, the sender will stop sending until ACK has been received
- `/proc/sys/net/ipv4/tcp_window_scaling` when set to 1, the kernel will attempt to start negotiate window scaling
- Only works if supported by both sides

Jumbo Frames:
- The default Maximum Transmission Unit (MTU) used on Ethernet is 1500 bytes, with a TCP protocol header of 52 bytes that is a bit of overhead
- Jumbo frames can be used to increase the MTU to higher than the Ethernet standard
- Jumbo frames need to be supported on **every** element in the network communication, this is hard to do sometime
- Jumbo frames are commonly seen on storage area network (SAN)
- The maximum jumbo frame size is 9000 bytes, and can be set with `nmcli`
- `nmcli con modify ens160 802-3-ethernet.mtu 9000`
- You can use `nmtui` to set the MTU
- `nmcli con down ens160 && nmcli con up ens160`
